Toàn bộ nằm dưới prefix `admin/crm`, gate **`@RequireFunction('users')`** ở CẤP CLASS (khuôn `CskhActivityController`).

| # | Endpoint | Trả về |
|---|---|---|
| 1 | `GET admin/crm/tag-catalog` | `string[]` — danh mục nhãn từ `system_config.CRM_CUSTOMER_TAGS`, ngăn cách `;`, có fallback hardcode |
| 2 | `GET admin/crm/customers/:id/tags` | `CrmTag[]` |
| 3 | `POST admin/crm/customers/:id/tags` body `{ tag }` | `CrmTag` (409 `CRM_TAG_DUP` nếu trùng) |
| 4 | `DELETE admin/crm/customers/:id/tags/:tagId` | `{ ok: true }` — **xoá cứng** |
| 5 | `GET admin/crm/customers/:id/notes?page&limit` | `{ data: CrmNote[], meta }` — chỉ dòng `deletedAt IS NULL` |
| 6 | `POST admin/crm/customers/:id/notes` body `{ note }` | `CrmNote` |
| 7 | `DELETE admin/crm/customers/:id/notes/:noteId` | `{ ok: true }` — **xoá mềm**, chỉ người viết hoặc super admin |
| 8 | `GET admin/crm/customers/:id/source` | `CrmCustomerSource \| null` |
| 9 | `GET admin/crm/customers/:id/timeline?days&limit&cursor&sources` | `{ data: CrmTimelineItem[], nextCursor: string \| null }` |

```ts
type CrmTag  = { id: string; tag: string; createdAt: string; byAdminUserId: string; byAdminName: string | null };
type CrmNote = { id: string; note: string; createdAt: string; byAdminUserId: string; byAdminName: string | null };

type CrmCustomerSource = {
  referrer: { id: string; fullName: string | null; phone: string | null; kind: 'KOL' | 'AFFILIATE' };
  codeUsed: string;
  referredAt: string;      // ISO có offset
};

type CrmTimelineKind =
  | 'CALL' | 'TRIP_CREATED' | 'TRIP_COMPLETED' | 'RATING' | 'NOTE' | 'NOTIFICATION';

type CrmTimelineItem = {
  id: string;              // id của DÒNG NGUỒN (booking sinh 2 mốc -> trùng id, khác kind)
  kind: CrmTimelineKind;
  occurredAt: string;      // ISO có offset, ĐÃ chuẩn hoá timestamptz
  title: string;           // dòng chính, tiếng Việt do BE sinh cho các mốc hệ thống
  detail: string | null;   // ghi chú / bình luận / lý do
  meta: Record<string, string | number | null>; // vd { stars: 5 }, { status: 'CALLED' }, { bookingId }
  byAdminUserId: string | null;
  byAdminName: string | null;
};
```

**Tham số `timeline`:**

| Param | Mặc định | Nghĩa |
|---|---|---|
| `days` | `90` | Cửa sổ `occurredAt >= now() - interval 'N days'`. Kẹp trần `730`. §11 rủi ro #2 |
| `limit` | `30` | Kẹp trần `100` |
| `cursor` | — | Xem "Cursor" dưới. Sai định dạng → **400**, KHÔNG im lặng rơi về trang 1 |
| `sources` | CSV, mặc định `CALL,TRIP_CREATED,TRIP_COMPLETED,RATING,NOTE` | `NOTIFICATION` là **opt-in** — xem "Sai khác so với spec" #1 |

**Cursor — 3 thành phần, KHÔNG phải 2:**

`base64("<occurredAtKey>|<kind>|<id>")`, trong đó `occurredAtKey` do **SQL tự phát ra** bằng
`to_char(occurredAt AT TIME ZONE 'UTC', 'YYYY-MM-DD"T"HH24:MI:SS.US"Z"')`.

- Phải có `kind`: một dòng `booking` sinh **hai** mốc (`TRIP_CREATED` + `TRIP_COMPLETED`) mang **cùng `id`**. Cursor 2 thành phần `(occurredAt, id)` sẽ nuốt hoặc lặp đúng ở ranh giới trang.
- Phải lấy chuỗi từ SQL chứ không từ JS `Date`: Postgres `now()` phân giải **micro giây**, driver `pg` parse thành `Date` chỉ giữ **mili giây** — mất 3 chữ số ⇒ dòng có phần lẻ `.123456` bị lặp (làm tròn xuống) hoặc bị nuốt (làm tròn lên). Mọi nguồn đều `DEFAULT now()`, không nguồn nào khai `timestamp(3)`.
- So sánh theo bộ ba: `(occurredAt, kind, id) < ($ts::timestamptz, $kind, $id::uuid)`, `ORDER BY occurredAt DESC, kind DESC, id DESC`.

 *

```sql
SELECT ev.*,
       to_char(ev."occurredAt" AT TIME ZONE 'UTC', 'YYYY-MM-DD"T"HH24:MI:SS.US"Z"') AS "cursorKey",
       a."fullName" AS "byAdminName"
  FROM ev
  LEFT JOIN "user" a ON a.id = ev."byAdminUserId"
 WHERE ev."occurredAt" >= now() - make_interval(days => $N)
   [AND (ev."occurredAt", ev.kind, ev.id) < ($ts::timestamptz, $kind, $id::uuid)]
 ORDER BY ev."occurredAt" DESC, ev.kind DESC, ev.id DESC
 LIMIT $LIM
```

Ghi chú bắt buộc trong code:

## Sai khác so với spec — cần bạn xác nhận

1. **`notification` KHÔNG nằm trong tập nguồn mặc định của timeline** (bật bằng công tắc "Hiện cả thông báo tự động"). Spec §5.1/§5.3 liệt nó như một nguồn ngang hàng. Lý do đổi: `sendPushToUser` **luôn** ghi một dòng `notification` trước khi bắn push và có ~36 call site, cộng fan-out broadcast — một khách 5 chuyến sẽ có ~15–20 dòng thông báo so với 5 dòng chuyến và vài dòng cuộc gọi. Để mặc định BẬT là nhấn chìm đúng thứ CSKH cần tìm, và kết luận rút ra sẽ là "timeline vô dụng" chứ không phải "lọc sai". **Index `notification` vẫn ship ở GĐ2** vì nó vá đường đọc thông báo của app khách/tài xế, độc lập với quyết định này.

2. **Timeline không gồm `crm_customer_tag`.** Nhãn là *trạng thái hiện tại*, hiện dạng chip ở khối tag; và vì gỡ nhãn là xoá cứng nên mốc "đã gắn nhãn" sẽ tự bốc hơi khỏi timeline — một dòng lịch sử biến mất được là tệ hơn không có dòng đó. Nếu bạn muốn ghi vết gắn/gỡ nhãn thì đó là một bảng event riêng, thuộc GĐ3.

3. **§13.7 giao đích danh cho GĐ2 quyết định che SĐT + audit log việc ĐỌC hồ sơ 360 — plan đề xuất HOÃN sang GĐ4, cần bạn chốt.** Lập luận: mức lộ mà §11 #8 lo là "SĐT **+ tuyến quen + khung giờ quen** + timeline gom một chỗ", mà **tuyến quen / khung giờ quen thuộc GĐ4**. GĐ2 mới gom "SĐT + timeline", tức mức lộ chưa vượt ngưỡng cũ. Ngược lại, backend **hiện không có bảng audit nào**, nên làm audit ở GĐ2 là đẻ thêm một bảng + một đường ghi nằm ngoài "2 bảng nhỏ + 1 index + 1 endpoint" mà §9 hứa. **Nếu bạn muốn làm ngay thì phải nói trước khi code** — nó đổi số bảng migration của GĐ2.

4. **Ai có function `users` thì GHI được tag và ghi chú về khách** — gồm role `cskh` (tuyến đầu), `quan-ly-chung`, `full-access-legacy`. Đây là hệ quả trực tiếp của việc **không đẻ function RBAC mới** (thứ giữ cho GĐ2 ở mức rủi ro thấp và né trọn bài học §13.1). Nếu bạn muốn tách quyền ghi ghi chú khỏi quyền xem hồ sơ thì phải nói **bây giờ**: sau này đổi gate là **TƯỚC** quyền của role đang dùng, phải làm bằng any-of chứ không thay thế.

5. **Danh mục nhãn `CRM_CUSTOMER_TAGS` chỉ SUPER ADMIN sửa được.** Spec §5.2 hứa "ops sửa không cần deploy, đúng mẫu `CSKH_CALL_REASONS`" — đúng một nửa. Key rơi vào nhóm `settings.misc` (catch-all trong `settingsGroupForKey` / `system-config-groups.ts`), mà `settings.misc` **không được cấp cho bất kỳ starter role nào** (quyết định 2026-07-23: "chỉ super sửa"). Chữa bằng cách thêm nhóm settings mới thì phải sửa mirror FE↔BE **và** đẻ migration cấp quyền — tức GĐ2 tự biến mình thành đúng cái bẫy §13.1. **Plan chọn để nguyên và nói thẳng.**

6. **Phân trang timeline bằng cursor, không phải OFFSET — nhưng KHÔNG vì tốc độ.** Dữ liệu prod rất nhỏ (7.908 chuyến toàn bộ lịch sử; `driver_trip_rating` ≤ 308 dòng), nên OFFSET vẫn chạy tốt và repo **không có tiền lệ cursor SQL nào** để chép. Lý do chọn cursor là **tính ổn định**: timeline là tập append liên tục, OFFSET sẽ lặp/nhảy dòng khi có sự kiện mới chèn vào lúc CSKH đang cuộn. Nếu bạn muốn rút gọn về OFFSET để ship nhanh (khuôn `CskhActivityService.getFeed` có sẵn), nói trước — nó bỏ được Task 5 Step 1–4 và một phần integration spec.

7. **"Nguồn khách" đi bằng endpoint RIÊNG, không thêm field vào `GET /users/admin/:id`.** Spec §3.4 chỉ nói "hồ sơ 360 có trường Nguồn khách", không nói đường nào. 9. **Sửa §5.3 điều kiện 1 của spec:** câu "mọi nhánh phải ép tường minh về `timestamptz`" là **nguy hiểm nếu hiểu theo nghĩa đen** — hai nguồn đã là `timestamptz`, ép thêm sẽ HẠ kiểu và lệch 7h theo chiều ngược.
